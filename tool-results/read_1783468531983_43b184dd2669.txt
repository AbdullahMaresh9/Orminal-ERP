    56→# **2.1 Backend Architecture Overview**
    57→
    58→## **2.1.1 Backend Responsibility**
    59→
    60→The backend layer is responsible for executing enterprise business
    61→logic, not only exposing APIs. It receives user and integration
    62→requests, applies permission and policy checks, executes use cases,
    63→coordinates workflows, performs posting orchestration, persists state,
    64→emits events, writes audit trails, runs background jobs and provides
    65→secure query models for frontend and reporting consumers.
    66→
    67→-   Receive commands and queries from the API layer.
    68→
    69→-   Execute business use cases and module-specific application logic.
    70→
    71→-   Apply authorization, data scope, field scope and
    72→    segregation-of-duties policies.
    73→
    74→-   Manage document lifecycle and workflow transitions.
    75→
    76→-   Execute business rules and validations consistently.
    77→
    78→-   Coordinate accounting posting and inventory posting through shared
    79→    services.
    80→
    81→-   Create domain events and integration events.
    82→
    83→-   Persist aggregate state through repositories and unit of work.
    84→
    85→-   Record audit events for critical actions.
    86→
    87→-   Run background jobs, integration jobs and event publishing workers.
    88→
    89→## **2.1.2 Backend Boundary**
    90→
    91→The backend boundary protects the system from architectural leakage. UI,
    92→integrations and reports must not directly modify operational data.
    93→Controllers must not contain business logic, posting logic or workflow
    94→decisions.
    95→
    96→  -----------------------------------------------------------------------
    97→  **Allowed in Backend**              **Forbidden in Backend Boundary**
    98→  ----------------------------------- -----------------------------------
    99→  Application use cases,              UI visual layout logic or component
   100→  command/query handlers, domain      rendering logic.
   101→  services, repositories and          
   102→  infrastructure adapters.            
   103→
   104→  Business rules, workflows, posting  Direct database writes from
   105→  orchestration, audit and            frontend or external systems.
   106→  authorization.                      
   107→
   108→  DTO mapping, validation pipeline,   SQL scattered inside controllers or
   109→  transaction pipeline and event      external clients.
   110→  publishing.                         
   111→
   112→  Controlled read models and query    Business validation that exists
   113→  services.                           only in frontend.
   114→  -----------------------------------------------------------------------
   115→
   116→Correct flow:\
   117→Frontend → API Controller → Application Layer → Domain Layer →
   118→Infrastructure\
   119→\
   120→Forbidden flow:\
   121→Frontend → Database\
   122→External Integration → Database\
   123→Controller → SQL → Posting tables
   124→
   125→## **2.1.3 Backend Design Goals**
   126→
   127→  -----------------------------------------------------------------------
   128→  **Goal**                            **Backend Meaning**
   129→  ----------------------------------- -----------------------------------
   130→  Domain Integrity                    Every state-changing operation
   131→                                      passes through the correct
   132→                                      aggregate, domain service or
   133→                                      policy.
   134→
   135→  Posting Safety                      No accounting or inventory posting
   136→                                      occurs outside the approved posting
   137→                                      services.
   138→
   139→  Workflow Consistency                Every state transition goes through
   140→                                      workflow service and is
   141→                                      audit-logged.
   142→
   143→  Security Enforcement                Every command and query evaluates
   144→                                      permissions, scopes and field-level
   145→                                      security.
   146→
   147→  Auditability                        Every critical action produces
   148→                                      traceable audit evidence.
   149→
   150→  Testability                         Every rule, policy, use case,
   151→                                      posting and workflow is testable in
   152→                                      isolation and integration.
   153→
   154→  Maintainability                     Commands, queries, domain logic and
   155→                                      infrastructure are separated.
   156→
   157→  Scalability                         Heavy side effects run
   158→                                      asynchronously through queues and
   159→                                      workers when appropriate.
   160→
   161→  Integration Safety                  External calls use idempotency
   162→                                      keys, correlation IDs, retries and
   163→                                      error mapping.
   164→  -----------------------------------------------------------------------
   165→
   166→## **2.1.4 Backend Non-Goals**
   167→
   168→-   Implementing financial or inventory business logic inside stored
   169→    procedures as a substitute for the domain layer.
   170→
   171→-   Allowing frontend to bypass workflow, authorization or posting
   172→    services.
   173→
   174→-   Making every module an independent microservice from the first
   175→    release.
   176→
   177→-   Duplicating authorization logic separately inside every module.
   178→
   179→-   Executing heavy analytics directly through transactional queries
   180→    when read models are required.

   205→## **2.2.2 Presentation / API Controllers**
   206→
   207→API Controllers are thin entry points. They receive HTTP requests,
   208→extract execution context, call mediator/handlers and return
   209→standardized responses. They must not implement decisions that belong to
   210→application or domain layers.
   211→
   212→Controller must not:\
   213→- Access database directly\
   214→- Build journal entries directly\
   215→- Change document status directly\
   216→- Send notifications directly\
   217→- Apply approval logic directly
   218→
   219→## **2.2.3 Application Services**
   220→
   221→The application layer represents use cases. It coordinates the execution
   222→of commands and queries according to the domain model, workflow engine,
   223→posting engine, audit service and outbox/event architecture.
   224→
   225→Examples:\
   226→ConfirmSalesOrderCommandHandler\
   227→PostCustomerInvoiceCommandHandler\
   228→ValidateGoodsReceiptCommandHandler\
   229→ApprovePurchaseOrderCommandHandler\
   230→RunPayrollCommandHandler\
   231→CloseFiscalPeriodCommandHandler
   232→
   233→-   Orchestrate use case execution.
   234→
   235→-   Load aggregates and required data.
   236→
   237→-   Call domain behavior and policies.
   238→
   239→-   Open and control transaction boundaries.
   240→
   241→-   Call workflow service where state transition is needed.
   242→
   243→-   Call posting service if financial or inventory posting is required.
   244→
   245→-   Save changes through unit of work.
   246→
   247→-   Record audit events and save outbox events.

   334→# **2.3 Domain Layer**
   335→
   336→## **2.3.1 Entities**
   337→
   338→An entity has identity and lifecycle. It protects its own invariants and
   339→exposes business methods, but it does not access the database, call
   340→external services or know about the UI/API.
   341→
   342→Examples:\
   343→Customer\
   344→Supplier\
   345→Product\
   346→SalesOrder\
   347→PurchaseOrder\
   348→JournalEntry\
   349→StockMove\
   350→ProductionOrder\
   351→Employee\
   352→Project\
   353→Asset\
   354→\
   355→Business methods:\
   356→SalesOrder.confirm()\
   357→SalesOrder.cancel(reason)\
   358→PurchaseOrder.approve(approver)\
   359→JournalEntry.post()\
   360→StockTransfer.validate()
   361→
   362→-   Entity must not depend on database directly.
   363→
   364→-   Entity must not call external services.
   365→
   366→-   Entity must protect its own invariants.
   367→
   368→-   Entity methods must represent business actions, not data setters
   369→    only.

   663→# **2.5 Infrastructure Layer**
   664→
   665→## **2.5.1 Database Access**
   666→
   667→Application Handler → Repository / Query Service → ORM / SQL → Database
   668→
   669→Controllers, frontend clients and external integrations must not access
   670→the database directly. All persistence must pass through approved
   671→repository/query/service boundaries.
   672→
   673→## **2.5.2 ORM Strategy**
   674→
   675→The ORM should be used for aggregates, transactional entities, master
   676→data and configuration where object mapping improves maintainability.
   677→Heavy reports may use optimized SQL, read models, materialized views or
   678→a reporting store.
   679→

   681→
   682→  -----------------------------------------------------------------------
   683→  **Repository Type**                 **Purpose**
   684→  ----------------------------------- -----------------------------------
   685→  Aggregate Repository                Load and save aggregate roots.
   686→
   687→  Read Repository                     Optimized query reads and
   688→                                      list/detail projections.
   689→
   690→  Lookup Repository                   Lightweight dropdown and reference
   691→                                      data queries.
   692→
   693→  Posting Repository                  Persist ledger and posting records.
   694→
   695→  Audit Repository                    Persist and query audit events.
   696→
   697→  Configuration Repository            Access versioned settings and
   698→                                      rules.
   699→  -----------------------------------------------------------------------
   700→
   701→## **2.5.4 Unit of Work**
   702→
   703→The Unit of Work coordinates transaction lifecycle. It opens the
   704→transaction, tracks changes, commits, rolls back and saves outbox events
   705→inside the same transaction.
   706→
   707→Commit Rule:\
   708→No external side effect before successful commit.
   709→

   711→
   712→  -----------------------------------------------------------------------
   713→  **Cache Use**                       **Allowed? / Rule**
   714→  ----------------------------------- -----------------------------------
   715→  Permissions cache                   Allowed; must invalidate after

   717→
   718→  Reference data cache                Allowed for stable data such as
   719→                                      currencies and UOMs.
   720→
   721→  Configuration cache                 Allowed with version-aware

   759→error mapping

   761→# **2.6 Repository Pattern**
   762→
   763→## **2.6.1 Repository Responsibility**
   764→
   765→Repositories do not contain business logic. They load aggregates, save
   766→aggregate state, execute persistence operations and enforce
   767→persistence-level constraints only.
   768→
   769→## **2.6.2 Aggregate Repository Rules**
   770→
   771→Allowed:\
   772→SalesOrderRepository.getById()\
   773→SalesOrderRepository.save()\
   774→PurchaseOrderRepository.getById()\
   775→JournalEntryRepository.save()\
   776→\
   777→Forbidden in repository:\
   778→approveOrder()\
   779→calculateTax()\
   780→postInvoice()
   781→
   782→## **2.6.3 Read Repository Rules**
   783→
   784→SalesOrderReadRepository.search()\
   785→StockOnHandReadRepository.getByWarehouse()\
   786→TrialBalanceReadRepository.run()
   787→
   788→Read repositories may use optimized SQL/read models, but must still
   789→enforce authorization and data scope rules.
   790→
   791→## **2.6.4 Repository Anti-Patterns**
   792→
   793→-   God repository combining unrelated modules.
   794→
   795→-   Repository per table without domain meaning.
   796→
   797→-   SQL inside controller.
   798→
   799→-   Business decisions inside repository.
   800→
   801→-   Bypassing unit of work.
   802→
   803→# **2.7 Unit of Work**
   804→
   805→  -----------------------------------------------------------------------
   806→  **Topic**                           **Rule**
   807→  ----------------------------------- -----------------------------------
   808→  Transaction Scope                   Aggregate update, workflow
   809→                                      transition, posting records, audit
   810→                                      records and outbox events.
   811→
   812→  Commit Rules                        Commit only after validations,
   813→                                      policies, postings and audit/outbox
   814→                                      preparation succeed.
   815→
   816→  Rollback Rules                      Rollback on validation failure,
   817→                                      posting failure, concurrency
   818→                                      conflict, database constraint
   819→                                      violation or unauthorized action.
   820→
   821→  Posting Transaction Rules           Document state change + posting +
   822→                                      audit + outbox must be in one
   823→                                      transaction.
   824→
   825→  Outbox Commit Rules                 Outbox event is saved before
   826→                                      commit; publish occurs after
   827→                                      commit.
   828→  -----------------------------------------------------------------------

   927→                                      controller checks.
   928→

   930→                                      only, not read-only queries.

  1029→## **2.10.7 Dependency Injection**
  1030→
  1031→Every service, repository, adapter and provider must be injected through
  1032→dependency injection. Static service locators, hard-coded providers and
  1033→creating external clients inside handlers are forbidden.
  1034→
  1035→## **2.10.8 Concurrency**
  1036→
  1037→-   Use optimistic concurrency for drafts and editable documents.
  1038→
  1039→-   Use version columns to detect stale updates.
  1040→
  1041→-   Use row locks for posting and sequence generation.
  1042→
  1043→-   Use unique constraints for idempotency keys and external references.
  1044→
  1045→## **2.10.9 Performance**
  1046→
  1047→-   No unbounded queries.
  1048→
  1049→-   No N+1 query patterns.
  1050→
  1051→-   Pagination is mandatory for lists.
  1052→
  1053→-   Use projections for dashboards.
  1054→
  1055→-   Batch operations run asynchronously when large.
  1056→
  1057→-   SQL plans and slow queries are monitored.

  1151→# **2.13 Backend Coding Guidelines**
  1152→
  1153→## **2.13.1 Command Handler Rules**
  1154→
  1155→-   1\. Authorize user and data scope.
  1156→
  1157→-   2\. Validate request DTO.
  1158→
  1159→-   3\. Load aggregate.
  1160→
  1161→-   4\. Apply policies/specifications.
  1162→
  1163→-   5\. Execute domain behavior.
  1164→
  1165→-   6\. Apply workflow transition.
  1166→
  1167→-   7\. Execute posting if required.
  1168→
  1169→-   8\. Record audit event.
  1170→
  1171→-   9\. Save outbox events.
  1172→
  1173→-   10\. Commit transaction.
  1174→
  1175→## **2.13.2 Query Handler Rules**
  1176→
  1177→-   Apply data scope.
  1178→
  1179→-   Apply field masking.
  1180→
  1181→-   Use pagination.
  1182→
  1183→-   Do not change state.
  1184→
  1185→-   Do not publish events.
  1186→
  1187→-   Audit only sensitive queries.
  1188→
  1189→## **2.13.3 Entity Rules**
  1190→
  1191→-   Entity does not know API.
  1192→
  1193→-   Entity does not know UI.
  1194→
  1195→-   Entity does not know database.
  1196→
  1197→-   Entity contains business invariants.
  1198→
  1199→-   Entity does not use service locator.
  1200→
  1201→## **2.13.4 Aggregate Rules**
  1202→
  1203→-   Protect consistency boundary.
  1204→
  1205→-   Child entities are modified only through aggregate root.
  1206→
  1207→-   Raise domain events.
  1208→
  1209→-   Own state transition methods.
  1210→
  1211→## **2.13.5 Service Rules**
  1212→
  1213→-   Single responsibility.
  1214→
  1215→-   Interface-driven.
  1216→
  1217→-   Testable.
  1218→
  1219→-   No hidden side effects.
  1220→
  1221→-   Use shared logging/audit services.
  1222→
  1223→## **2.13.6 Exception Rules**
