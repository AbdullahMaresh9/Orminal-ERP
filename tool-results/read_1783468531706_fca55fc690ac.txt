    56→# **5.1 Frontend Architecture Vision**
    57→
    58→## **5.1.1 Frontend Mission**
    59→
    60→The frontend is not a passive presentation layer. In an enterprise ERP
    61→platform, it is the role-based productivity environment where users
    62→execute transactions, approve workflows, analyze exceptions, inspect
    63→audit history, manage documents and interact with operational controls.
    64→It must translate complex ERP behavior into a disciplined, consistent,
    65→secure and efficient user experience.
    66→
    67→Frontend Mission:\
    68→Enterprise Workspace\
    69→Role-Based Productivity Environment\
    70→Transaction Execution Platform\
    71→Workflow Interaction Layer\
    72→Decision Support Layer\
    73→Operational Control Center
    74→
    75→Goal:\
    76→Enable enterprise users\
    77→to execute business processes\
    78→with maximum efficiency,\
    79→minimum clicks,\
    80→clear visibility,\
    81→full traceability,\
    82→and secure access.
    83→

    85→
    86→  -----------------------------------------------------------------------

    90→                                      shortcuts, quick actions, saved
    91→                                      filters, role workspaces and bulk
    92→                                      operations.
    93→
    94→  Consistency                         Use the same object page, list,
    95→                                      table, workflow, attachment,
    96→                                      timeline and audit patterns across
    97→                                      modules.
    98→

   100→                                      through feature-first modules and
   101→                                      shared component architecture.
   102→
   103→  Maintainability                     Keep UI, state, routes, services
   104→                                      and feature modules separated and
   105→                                      testable.
   106→
   107→  Extensibility                       Enable new ERP modules, reports and
   108→                                      screens without breaking shell,
   109→                                      navigation or core components.
   110→

   212→# **5.3 Flutter Architecture**
   213→
   214→## **5.3.1 Feature-First Architecture**
   215→
   216→The frontend must use a feature-first architecture. ERP scale makes a
   217→layer-first global structure difficult to maintain because hundreds of
   218→screens and thousands of widgets become mixed across modules.
   219→Feature-first keeps sales, finance, inventory and HR independent while
   220→still sharing common design components.
   221→
   222→Forbidden global structure:\
   223→/screens\
   224→/widgets\
   225→/services\
   226→/models\
   227→\
   228→Approved feature-first structure:\
   229→/features\
   230→/sales\
   231→/inventory\
   232→/finance\
   233→/purchasing\
   234→/hr
   235→
   236→  -----------------------------------------------------------------------
   237→  **Architecture Rule\
   238→  **The feature module owns its pages, state, DTO mappings, validators,
   239→  route definitions and tests. Shared widgets live in shared/ui only when
   240→  they are genuinely reusable.

   314→# **5.4 State Management Architecture**
   315→
   316→## **5.4.1 State Strategy**
   317→
   318→The platform requires enterprise-grade state management that is
   319→scalable, testable, modular, predictable and friendly to asynchronous
   320→workflows. State must support large forms, approval actions, dashboards,
   321→offline queues and long-running background jobs.
   322→
   323→State management criteria:\
   324→Scalable\
   325→Testable\
   326→Modular\
   327→Predictable\
   328→Event Driven
   329→
   330→## **5.4.2 Recommended Approach**
   331→
   332→The recommended frontend state architecture is Riverpod with
   333→StateNotifier, AsyncNotifier, Provider, FutureProvider and
   334→StreamProvider. Riverpod is selected because it supports explicit
   335→dependencies, testability, modular providers, scoped overrides and clean
   336→separation from widget lifecycle.
   337→
   338→  -----------------------------------------------------------------------
   339→  **Riverpod Construct**              **Recommended Use**
   340→  ----------------------------------- -----------------------------------
   341→  Provider                            Immutable dependencies, API
   342→                                      clients, configuration and service
   343→                                      access.
   344→
   345→  StateNotifierProvider               Complex mutable screen/form state
   346→                                      where explicit actions are
   347→                                      required.
   348→
   349→  AsyncNotifierProvider               Asynchronous screen state such as
   350→                                      lists, details, reports and
   351→                                      dashboards.
   352→
   353→  FutureProvider                      Simple one-time lookups and
   354→                                      reference data.
   355→
   356→  StreamProvider                      Live updates, notifications, job
   357→                                      progress and event-driven screen
   358→                                      updates.
   359→  -----------------------------------------------------------------------
   360→

   397→
   398→## **5.4.4 State Rules**
   399→
   400→-   Business logic must not live inside widgets.
   401→
   402→-   API calls must not be executed directly inside UI build methods.
   403→
   404→-   Global mutable state is forbidden.
   405→
   406→-   Every asynchronous state must expose loading, empty, success and
   407→    error states.
   408→
   409→-   Form states must track dirty/clean status for unsaved change
   410→    warnings.
   411→
   412→-   State must be recoverable after navigation when business flow
   413→    requires it.
   414→
   415→-   Permission changes must invalidate permission-dependent UI state.

   417→# **5.5 Routing Architecture**
   418→
   419→## **5.5.1 Routing Strategy**
   420→
   421→The application uses declarative routing. Routes are defined per feature
   422→and registered into the app shell through a central route registry.
   423→Route guards enforce authentication, permissions, data scope and
   424→license/module availability before rendering screens.

   741→# **5.11 Offline Architecture**
   742→
   743→## **5.11.1 Offline Goals**
   744→
   745→Offline support is selective and controlled. It is intended for weak,
   746→intermittent or temporary offline conditions, not for permanent offline
   747→ERP operation. Offline transactions must be queued, validated locally
   748→where possible and revalidated by backend during sync.
   749→
   750→## **5.11.2 Cached Data**
   751→
   752→Lookups\
   753→Currencies\
   754→Permissions\
   755→User Preferences\
   756→Recent Documents\
   757→Warehouse Locations\
   758→Product Barcodes\
   759→Open Assigned Tasks
   760→
   761→## **5.11.3 Offline Queue**
   762→
   763→The offline queue stores create/update commands, attachments and user
   764→actions until synchronization. Each queued item requires local ID,
   765→command type, payload, timestamp, user, company, retry count and sync
   766→status.
   767→
   768→  -----------------------------------------------------------------------
   769→  **Offline Queue Field**             **Purpose**
   770→  ----------------------------------- -----------------------------------
   771→  local_id                            Temporary client-side identifier.
   772→
   773→  command_type                        Business action type such as
   774→                                      CreateStockCountLine.
   775→
   776→  payload                             Serialized command payload.
   777→
   778→  created_at                          Offline creation timestamp.
   779→
   780→  user_id                             Actor who created the command.
   781→
   782→  company_id                          Company context.
   783→
   784→  retry_count                         Sync retry count.
   785→
   786→  sync_status                         Pending, syncing, failed, synced or
   787→                                      conflict.
   788→  -----------------------------------------------------------------------
   789→
   790→## **5.11.4 Conflict Resolution**
   791→
   792→  -----------------------------------------------------------------------
   793→  **Conflict Strategy**               **Use Case**
   794→  ----------------------------------- -----------------------------------
   795→  Server Wins                         Financial postings, posted
   796→                                      documents, security-sensitive data.
   797→
   798→  Client Wins                         Limited low-risk drafts when no
   799→                                      server update occurred.
   800→
   801→  Manual Resolution                   Conflicting field edits, stock
   802→                                      counts, field service notes and
   803→                                      attachments.

  1040→# **5.17 Security on Frontend**
  1041→
  1042→## **5.17.1 Frontend Security Rules**
  1043→
  1044→Forbidden:\
  1045→Store JWT in insecure storage\
  1046→Client-side authorization only\
  1047→Expose hidden fields in API responses\
  1048→Hard-code secrets\
  1049→Trust route guards as the only security layer\
  1050→Log sensitive personal/financial data
  1051→
  1052→## **5.17.2 Required Security Controls**
  1053→
  1054→Secure Storage\
  1055→Refresh Tokens\
  1056→Permission-Based Rendering\
  1057→Mask Sensitive Data\
  1058→Session Timeouts\
  1059→Route Guards\
  1060→Sensitive Action Confirmation\
  1061→MFA hooks for high-risk actions\
  1062→Export Permission Checks
  1063→
  1064→## **5.17.3 Permission-Based Rendering**
  1065→
  1066→The UI must hide or disable actions based on permission metadata, but
  1067→backend remains the final authority. Buttons disabled due to permission
  1068→or workflow state should provide a short reason when appropriate,
  1069→especially for enterprise users and approvers.
