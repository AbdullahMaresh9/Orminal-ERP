    60→# **BOOK 1 --- Enterprise Software Architecture**
    61→
    62→## **1.1 Architectural Vision**
    63→
    64→The platform shall be a modular, domain-oriented, event-aware,
    65→audit-first ERP system with a single operational truth for finance,
    66→inventory, documents, approvals and master data. The system shall
    67→support multi-company operations, role-based workspaces, immutable
    68→posted transactions, append-only ledgers, governed extensibility and
    69→integration through secure APIs/events.
    70→
    71→## **1.2 Design Goals**
    72→
    73→-   Enable enterprise-grade financial and operational control without
    74→    copying any vendor architecture.
    75→
    76→-   Keep business logic in explicit domain services and policies rather
    77→    than hidden UI scripts.
    78→
    79→-   Make every legally relevant document traceable from source to
    80→    posting to report.
    81→
    82→-   Support configuration and extension without breaking upgradeability.
    83→
    84→-   Separate transactional workloads from analytical/reporting
    85→    workloads.
    86→
    87→-   Design for observability, auditability, recovery and compliance from
    88→    day one.
    89→

   195→## **1.6 Deployment Strategy**
   196→
   197→Deploy the platform as a modular service-oriented monolith at first,
   198→with strict internal bounded contexts and event contracts. Extract
   199→services only when scaling, compliance, deployment independence or team
   200→ownership justifies it. This avoids premature microservice complexity
   201→while preserving future decomposition paths.
   202→

   400→## **3.1 Navigation Consistency Rules**
   401→
   402→-   Every document list must expose status, owner, date,
   403→    amount/quantity, next action and risk indicator.
   404→
   405→-   Every object page must expose source documents, target documents,
   406→    accounting impact, inventory impact and audit.
   407→
   408→-   Every dashboard must distinguish KPI, exception, pending action and
   409→    trend.
   410→
   411→-   Every configuration page must show last modified by/date and
   412→    affected modules.
   413→
   414→-   Every menu item must have a unique menu code, permission code and
   415→    help reference.

   616→## **6.2 Physical Design Guidelines**
   617→
   618→-   Primary keys use opaque UUID/ULID or database-generated IDs;
   619→    document numbers are business keys, not primary keys.
   620→
   621→-   Foreign keys must be enforced for master references unless
   622→    high-volume event tables intentionally decouple with validated IDs.
   623→
   624→-   Every transaction table includes company_id, branch_id where
   625→    applicable, status, created_by, created_at, updated_by, updated_at.
   626→
   627→-   Posted financial and stock ledger tables are append-only; never
   628→    update amounts/quantities after posting except technical metadata.
   629→
   630→-   Indexes must support common filters: company, branch, date, status,
   631→    partner, product, warehouse, cost center, document number.
   632→
   633→-   Partition ledgers, stock moves, audit and event tables by
   634→    company/period when volume justifies it.
   635→
   636→-   Use optimistic concurrency version columns for drafts and
   637→    configuration; use posting locks for sequence and ledger posting.
   638→
   639→-   Soft delete allowed only for non-posted, non-legal configuration or
   640→    drafts; otherwise archive/block/cancel.

  1145→# **BOOK 15 --- Engineering Standards**
  1146→
  1147→  -----------------------------------------------------------------------
  1148→  **Standard Area**                   **Blueprint Standard**
  1149→  ----------------------------------- -----------------------------------
  1150→  Folder Structure                    Organize by bounded context/module;
  1151→                                      separate domain, application,
  1152→                                      infrastructure, API, UI, tests and
  1153→                                      migrations.
  1154→
  1155→  Coding Standards                    Clean code, typed DTOs, explicit
  1156→                                      errors, no hidden business rules in
  1157→                                      UI, no direct DB access from
  1158→                                      controllers.
  1159→
  1160→  Naming Conventions                  Consistent names for modules,
  1161→                                      entities, APIs, events, commands,
  1162→                                      permissions and configs.
  1163→
  1164→  Git Strategy                        Trunk-based or GitFlow-light with
  1165→                                      protected main, pull requests and
  1166→                                      release branches.
  1167→
  1168→  Commit Standards                    Conventional commits: feat, fix,
  1169→                                      refactor, docs, test, chore,
  1170→                                      security, migration.
  1171→
  1172→  Testing Standards                   Unit tests for policies/services;
  1173→                                      integration tests for
  1174→                                      posting/workflows; contract tests
  1175→                                      for APIs; E2E for critical flows.
  1176→
  1177→  Documentation                       ADRs, API OpenAPI, data
  1178→                                      dictionaries, workflow specs,
  1179→                                      screen specs and runbooks must be
  1180→                                      versioned.
  1181→
  1182→  CI/CD                               Automated build, tests, static
  1183→                                      analysis, dependency scan,
  1184→                                      migration validation and deploy
  1185→                                      gates.
  1186→
  1187→  Deployment                          Blue/green or rolling strategy;
  1188→                                      database migrations
  1189→                                      backward-compatible where possible.
  1190→
  1191→  Monitoring                          Every service exposes health,
  1192→                                      metrics, logs and traces.
  1193→
  1194→  Logging                             Structured JSON logs with
  1195→                                      correlation ID, user ID,
  1196→                                      tenant/company, action, document ID
  1197→                                      and severity.
  1198→
  1199→  Code Review                         Minimum two reviewers for
  1200→                                      finance/security/posting changes;
  1201→                                      checklist includes tests, audit,
  1202→                                      security and performance.
  1203→
  1204→  Quality Gates                       No critical security findings, no
  1205→                                      failing tests, migration dry-run
  1206→                                      pass, API contract pass,
  1207→                                      performance checks for hotspots.
  1208→
  1209→  Release Management                  Semantic versioning, release notes,
  1210→                                      migration plan, rollback plan,
  1211→                                      feature flags.
  1212→
  1213→  Technical Debt                      Logged, prioritized, owner assigned
  1214→                                      and reviewed in architecture board.
